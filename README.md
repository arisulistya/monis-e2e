# Monis E2E tests

Automated end-to-end test cases for Monis, built with TypeScript and Playwright.

## Test cases

- **Email login:** required fields, invalid email and password, successful login, account identity, and logout.
- **Email signup:** required fields, invalid email, password length and confirmation, and account creation.
- **Email login link:** required email and login through a received link.
- **Google:** sign-in button on login and signup forms, and sign-in with a dedicated account.
- **Storefront:** category and product browsing, matching and empty search results, product variants and rental options, bundle contents, guest cart persistence and clearing, rental guide, currency, and delivery city.

Account-dependent cases may be skipped when their prerequisites are missing. The public Mailinator email-link and automated Google sign-in flows have not yet been verified end to end.

The default environment file points to production at `https://www.monis.rent/`. Some tests can create accounts or request emails when explicitly enabled. Use dedicated test accounts and review the [production side effects](#production-side-effects-and-cleanup) before enabling them.

## Requirements

- Node.js 20 or newer and npm. The installed Playwright package requires Node.js 20 or newer.
- Java, available as `java`, to generate and open Allure reports.
- Internet access to install dependencies and reach the chosen Monis environment.
- A terminal opened in this repository. Examples use macOS or Linux shell syntax.

## First run

1. Install dependencies and Chromium for the local checks, and ensure Google Chrome is installed for the main suite:

   ```sh
   npm ci
   npx playwright install chromium
   ```

2. Create an ignored environment file in the project directory. The guard preserves an existing file:

   ```sh
   if [ ! -e .env ]; then
     cp .env.example .env
     chmod 600 .env
   fi
   ```

   Open that file in your editor. Confirm `BASE_URL` and add dedicated test credentials when needed. Do not commit or share the file. The supplied example targets production and leaves account creation disabled.

3. Check configuration and discover the tests without running them:

   ```sh
   npm run typecheck
   npm run test:list
   ```

4. Run the smoke suite:

   ```sh
   npm run test:smoke
   npm run report
   ```

   The smoke list contains four login and storefront cases. The login case requires a configured test account; otherwise it is skipped. Review the terminal summary and Allure report for passed, failed, and skipped cases. Missing prerequisites can also cause tests in the full suite to be skipped.

## Run tests

| Command | What it does |
| --- | --- |
| `npm test` | Run all discovered tests headlessly with up to two workers. |
| `npm run test:smoke` | Run the smoke test list headlessly. |
| `npm run test:weekly` | Run the current weekly test list headlessly. |
| `npm run test:regression` | Run the full suite headlessly. |
| `npm run test:headed` | Run with a visible browser and one worker. |
| `npm run test:debug` | Run with a visible browser, one worker, and Playwright Inspector. |
| `npm run test:ui` | Open Playwright UI mode. |
| `npm run test:list` | List tests without running them. |
| `npm run report` | Open the latest report generated by the run scripts. |

Headed and debug runs use a 500 ms Playwright `slowMo` setting. Add `--keep-open` to keep the browser open for three minutes after each test, including failures:

```sh
MONIS_ENV_FILE=.env.staging npm run test:headed -- e2e/tests/delivery-address --keep-open
```

The Chromium project runs at most one worker because delivery-address tests share a staging cart. Headed and debug commands also use one worker.

To run a specific file or select tests by title:

```sh
npm test -- e2e/tests/auth/login.spec.ts
npm test -- --grep 'requires a sign-up email'
```

The runner prints reasons for failed and skipped tests. A skipped test has not verified its expected behavior.

## Manage smoke and weekly test lists

The files in `plans/` select existing tests without copying test code. `plans/weekly/current.txt` is an example, not a release-specific plan. Edit it to match the changes you want to test that week.

Each entry has an exact path and test title, relative to `e2e/tests/`:

```text
auth/login.spec.ts > signs in with the dedicated account and signs out
journey/storefront.spec.ts > search reports when there is no matching product
```

Copy paths and titles from `npm run test:list`, omitting the project and line numbers. Add one case per line. Lines starting with `#` are comments. Update a plan when a selected test moves or its title changes.

```sh
npm run test:plan-check -- plans/weekly/current.txt
npm run test:weekly
npm run test:headed -- --test-list=plans/weekly/current.txt
```

The run script validates planned entries against Playwright discovery. It rejects empty, duplicate, malformed, unknown, or ambiguous entries before the browser run. Planned runs cannot be combined with selection filters such as `--grep`, `--project`, or `--shard`; change the list instead. Calling `npx playwright test --test-list ...` directly bypasses the project validator. List order does not set execution order.

## Select an environment

The default file is the project’s `.env`. To prepare staging without overwriting an existing file:

```sh
if [ ! -e .env.staging ]; then
  sed 's|^BASE_URL=.*|BASE_URL=|' .env.example > .env.staging
  chmod 600 .env.staging
fi
```

Edit `.env.staging` and set `BASE_URL` to the staging URL and `STAGING_GATE_PASSWORD` to the staging access password. Use staging-specific accounts. Credentials are not supplied in this repository.

```sh
# Production: default environment file
npm run test:smoke

# Staging: explicitly select the staging file
MONIS_ENV_FILE=.env.staging npm run test:smoke
MONIS_ENV_FILE=.env.staging npm run test:headed
```

The selected file must exist and contain a valid `BASE_URL`. The run fails when the file or URL is missing; it does not fall back to production. Its `BASE_URL` and account values take precedence over values inherited from the shell. The shell can override `RUN_PRODUCTION_MUTATIONS` for one run. Allure records the target origin and selected plan.


## Environment variables

| Variable | Purpose |
| --- | --- |
| `BASE_URL` | Required target URL in the selected environment file. |
| `STAGING_GATE_PASSWORD` | Required for the staging site's password prompt; keep it in the private staging environment file. |
| `TEST_USER_EMAIL`, `TEST_USER_PASSWORD` | Dedicated existing Monis account for password login and logout. |
| `NEGATIVE_TEST_USER_EMAIL`, `NEGATIVE_TEST_USER_PASSWORD` | Optional separate account for the invalid-password test. |
| `MAILINATOR_TEST_EMAIL` | Separate existing Monis test account at a public `@mailinator.com` inbox for email-link login. |
| `AUTH_LINK_HOST` | Exact HTTPS hostname of the observed email login link. Never put a complete link or token here. |
| `GOOGLE_EMAIL`, `GOOGLE_PASSWORD` | Dedicated Google test account. Google can still require a challenge. |
| `RUN_PRODUCTION_MUTATIONS` | Set to `1` to allow account creation and email-link requests. The name applies even when the selected target is staging. |
| `MONIS_ENV_FILE` | Path to the environment file, supplied in the shell. Defaults to the project’s `.env`. |

A test skips when its required account or settings are missing. If the negative account is absent and mutations are enabled, the suite can create a separate disposable account. The email-link flow also requires the application to deliver a message to the configured inbox. Public Mailinator end-to-end delivery has not yet been verified for this suite.

## Production side effects and cleanup

With `RUN_PRODUCTION_MUTATIONS=1`, a full run can create two accounts and request a login email. The generated email addresses and target origins are appended to `~/.monis-e2e/.local/accounts-to-clean.txt` before signup, including when signup fails. The account owner must review and clean up the accounts manually. The suite does not delete accounts.

Mailinator public inboxes can be read by anyone. A public login link can grant access to its test account. Use disposable accounts with no private data and do not reuse passwords. A site may reject disposable addresses. Google may present MFA, CAPTCHA, or another challenge; the suite does not bypass it.

To enable account creation and email requests for one headed run:

```sh
RUN_PRODUCTION_MUTATIONS=1 npm run test:headed
```

Keep `.env` files, cleanup records, browser session state, screenshots, videos, traces, and reports private. They may contain email addresses, tokens, or account data.

## Reports and troubleshooting

Each `npm test`, `test:smoke`, `test:weekly`, `test:regression`, `test:headed`, or `test:debug` run creates an Allure report under `~/.monis-e2e/allure-runs/`. `npm run report` opens the latest one. Reports are separate per run; cross-run trends are not configured.

Executed tests with an open page capture a final screenshot. Failed tests retain a video and trace. Login and signup tests also capture signed-in and signed-out screenshots. Allure shows expected behavior, test steps, and an actual-behavior attachment. A skipped test or a failure before a page opens cannot provide a page screenshot or video.

- **Test skipped:** read the skip reason and configure its prerequisites. The terminal and `issues.txt` list skips and failures.
- **Timeout or failure:** open the test in Allure and inspect its failed step, screenshot, video, and trace. A changed product, stock level, selector, or a slow site can affect production runs.
- **Environment file error:** check `MONIS_ENV_FILE` and set a valid `BASE_URL` inside that file.
- **Plan validation error:** use `npm run test:list` to check the exact current test title, then update the plan.
- **Google or email login blocked:** check the dedicated account and provider prerequisites; do not bypass provider challenges.

Run the framework checks locally:

```sh
npm run typecheck
npm run test:environment
npm run test:plan-selfcheck
npm run test:mailinator
npm run test:staging-gate
```

The Mailinator check uses a local mock; it does not prove real email delivery. The main suite uses installed Google Chrome. Delivery-address tests require a real browser location and fail during setup if Chrome cannot obtain one. Checkout coverage beyond delivery address and Bill Details, cross-browser testing, and CI are not configured.
